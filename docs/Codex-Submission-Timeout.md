# Codex 发送确认超时处理

## 原因

`thread-follower-start-turn-timeout` 表示原生启动请求没有及时确认，不等于拒收。
原先接入端把该错误包装成通用拒绝异常，结束发送；即使随后消息被接收，客户端也无法进入成功后的草稿清理流程。

## 修复

- 原生 `*-timeout` 错误分类为超时，不再附加未经证实的版本兼容或拒收判断。
- 发送确认超时后，接入端最多继续等待两分钟，核对原消息的唯一客户端 ID；普通消息和已接受的执行中插入消息均支持。
- 收到对应记录后完成原发送请求，桌面和手机沿用成功后的草稿清理流程。不会重新发送，也不会以相同文本或 Agent 忙碌状态充当确认。
- 两分钟后仍无记录，返回“发送结果待确认，不代表 B 端拒收”，保留草稿。取消等待仍生效。
- 桌面仅清除对应会话中未改动的已发送草稿；后来编辑的内容和另一会话的草稿保留。

等待窗口加原生请求约 28 秒，小于客户端三分钟发送 RPC 期限。窗口过后才到达或不含可匹配消息 ID 的记录仍无法自动确认，不能据此承诺任意延迟都能自动清理。
