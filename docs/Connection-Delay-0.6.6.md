# 0.6.6 收包、界面积压与发送确认

## 发现及证据边界

用户报告：回复长时间不可见，发送询问后提示超时，随后消息成功发出且旧回复集中出现。本次最初查询客户端仍为 connected=true；旧版没有断线/收包时间记录，因此不能事后证明该次确实是空闲断线。

代码存在可复现的调度问题：WPF 在 UI 上调用 RpcPeer.Start，原实现直接启动异步接收循环，导致异步继续执行依赖界面调度。长会话渲染可拖慢接收。已用一个不处理回调的 SynchronizationContext 验证新接收循环仍能收到通知。

另一个确定的语义问题是 RPC 40 秒确认期限：超时只停止本地等待，不撤销已交付远端的请求。远端后续执行完毕、历史回读更新，可产生“报超时后又成功”的表现；没有证据证明客户端自行重发了消息。Hermes 端轮询和发送还共享适配器锁，慢请求可能使确认变迟，本次不改动线上接入端。

## 修改

- RPC 收包/请求处理从调用者的 UI 同步上下文中分离。
- WPF 每 250 毫秒消费最新会话快照，只留一个待显示状态，避免过时快照大量排队。RPC 结果、审批应答和文件块不在此合并范围内；合并的是用于展示的完整会话状态，未删除服务器历史。
- WPF 发送 12 秒未确认时提示继续等待原请求，发送操作仍保持禁用；等待确认期限为 3 分钟。期限耗尽明确提示“结果未知，不代表失败”，不自动重发。此期限不是 AI 生成回复的时限。
- 本机 Status 新增 connectedAt、disconnectedAt、reconnectCount、lastReceivedAt、receivedMessages 和 lastRenderedAt。最后收包时间统计应用消息，不统计 WebSocket Ping/Pong；无消息时不能仅凭该时间判定掉线。lastRenderedAt 仅记录当前选中会话的显示处理。

## 验证

- 核心 127 项、WPF/持久化 16 项通过。
- 新增检查覆盖不运行 UI 调度时的收包、延迟应答完成同一原请求且只写出一次请求、真实接收时间和计数。
- 本地客户端实际切换为 0.6.6 并自动连上 Hermes-default。没有向用户的 Agent 会话发送测试指令，没有更新或重启中继/Hermes。
- 本次验证不是长时间空闲网络稳定性的证明。若再现，应结合新诊断时间区分断线重连、远端确认慢和显示更新慢。
